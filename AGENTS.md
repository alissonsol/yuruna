# Agent rules

These rules apply to every agent, tool, automation, provider, backend model and
model version, including delegated agents. Read them before changing files.

`AGENTS.md` is the single source of agent guidance in this repository. Keep the
complete policy here. Other agent instruction files, including `CLAUDE.md`,
must only direct the agent to read this repository's `AGENTS.md`, using a local
reference or a supported import. Do not duplicate the policy in those files.

Keep the canonical policy consistent across workspace repositories and use
repository-neutral language without hard-coded checkout names. Each repository
must contain its own complete `AGENTS.md`; do not depend on another checkout,
a machine-specific path or a private agent memory. Preserve `AGENTS.md` in
every distributed copy, including when publication excludes tool-specific files.

## Synchronize the entire workspace before changes

Before the first edit, file creation, staging operation or code-generating
command for a task, synchronize **every repository in the workspace**, even if
the task changes only one repository. Discover the repositories from the active
workspace instead of assuming a fixed list or directory layout. Do not start
changes anywhere until synchronization has succeeded everywhere.

1. Inspect each checkout's branch, upstream and `git status --short --branch`.
   Stay on its current branch. If any checkout has uncommitted work, an
   unfinished merge/rebase, no upstream or a detached HEAD, stop and ask the
   operator how to proceed. Never stash, reset or discard someone else's work.
2. In **each** checkout run `git -c rebase.autoStash=false pull --rebase`.
   This fetches upstream changes and rebases unpublished local commits when
   needed. Fetching alone or checking only the repository being edited does
   not satisfy this requirement. Never rewrite commits already published to
   a remote, force-push or select a blanket conflict winner.
3. If any pull fails or a rebase conflicts, stop before editing task files.
   Report the repository, error and conflicted files, and ask the operator
   for a decision. Preserve the in-progress state; do not silently abort,
   skip commits or continue with stale repositories.
4. Confirm every checkout has no commits behind its upstream and record its
   base commit with `git rev-parse --short HEAD`. Report any unpushed commits.

Complete this preflight before delegating edits. Revisions and verification
fixes within the same task continue from its completed preflight; do not pull
through in-progress edits just to repeat it. Start a new task or independent
batch with a new preflight.

## Preserve operator control of Git

Never commit or push automatically. Leave changes in the working tree for
review unless the operator explicitly and unambiguously authorizes the action
for the work at hand. Authorization for one change does not authorize later,
unrelated changes.

Work on the current branch, including when it is the default branch. Do not
create or switch branches, or move the work to another branch, unless the
operator explicitly requests it. Synchronization does not authorize commits,
pushes or branch changes.

Stage only files belonging to the authorized change. Preserve unrelated work.
Never bypass required checks to make a commit or push succeed.

## Keep commit messages free of tool comments and attribution

Commit messages must describe the actual change and necessary technical
rationale. No tool may add its own comments, credits, signatures, promotional
text or execution/session notes to a commit message.

- Never add a `Co-Authored-By:` trailer, regardless of capitalization, agent,
  backend model, model version, vendor or email address.
- Never add "Generated by", "Assisted by", "Committed by" or equivalent tool
  attribution, including agent names, model names, bot identities, and
  `noreply` / `no-reply` email credits.
- Use the operator's configured Git identity; do not substitute a tool identity
  or invent an author/email.
- Before committing, inspect the complete proposed message and any template,
  hook or tool option that could append attribution. Before pushing, inspect
  **every outgoing commit message** for these rules.
- Do not create or push a noncompliant commit. Correct only work whose history
  you are authorized to edit; otherwise ask the operator. Never rewrite
  published history to remove old attribution.

These rules apply equally to direct Git commands, generated messages, IDEs,
CLI tools, delegated agents and automated commit/push workflows.

## Read and plan before editing

Read the files you will change and the relevant callers, tests and local
documentation. Follow the existing style, architecture, interfaces and
dependencies. Understand the whole relevant behavior before editing.

Define the success criteria before implementation. State material assumptions
and tradeoffs, and give a brief plan for multi-step work. Ask for a human
decision when requirements, scope or architectural intent are unclear rather
than inventing an answer.

## Keep changes simple and focused

Write the smallest clear change that solves the requested problem. Preserve
unrelated behavior. Avoid speculative abstractions, unnecessary configuration,
unreachable error handling, dead code and unrelated refactors or formatting.
Every changed line should serve the task.

Reuse established patterns and existing dependencies. Prefer the language's
standard library when it suffices. Add a dependency only when necessary and
explain why. Do not generalize a single use case without a concrete need.

Watch for scope expansion, premature abstraction, missing failure paths and
refactors that spread into unrelated files. When these appear, reassess the
approach instead of continuing to broaden the change.

## Preserve operator configuration

A tool that rewrites a configuration file the operator owns, such as a test
configuration refreshed from its template or a setting an installer fills in,
keeps every value the operator set. A built-in default fills only an absent or
blank key and never replaces a value already present. Only a value the
operator supplied for that run replaces an existing one.

- Report every replaced value as `key: previous -> new`, never as the new
  value alone, and before the file is written. A line that names only the new
  value reads as confirmation to the operator whose value was just lost, and
  later runs then exercise the wrong target while every check stays green,
  because telemetry agrees with the configuration it was handed.
- Keep the previous value recoverable, through a backup or the reported line,
  and say where it is.
- Printing the resolved configuration at run start does not satisfy this rule;
  the comparison the operator needs is against the previous file.
- Every code path that writes such a file has a regression test that seeds a
  non-default operator value (for example a `file:///` project URL), re-runs
  the path with the built-in default and proves the value survived unchanged
  on disk. A path that may replace a value also proves the `previous -> new`
  report.

## Preserve standalone execution contracts

When a script is designed to run as a single downloaded or copied file, keep
it self-contained. Do not extract its required functions into companion files,
add hard module dependencies (including `Import-Module`, `using module` or
`#requires -Modules`), dot-source companion files, or require adjacent catalogs
or a checkout. Preserve its existing behavior when it is the only project file
present.

Intentional duplication that supports standalone execution is a design
constraint, not a refactoring or review finding. Where shared modules are the
source of truth, update the embedded copies when the source changes and keep
the equivalence and standalone-execution tests working.

An optional call into a module that the caller already loaded is acceptable
only when the script detects availability and retains a complete local
fallback. Refresh embedded message text using the repository's documented
catalog and generation process when messages change.

## Write durable comments and documentation

Comments explain why the code has its shape: constraints, invariants,
surprising behavior, external workarounds and documented regression classes.
They must not depend on the conversation or process that produced the change.

- Do not put audit/review/task IDs, refactor phases, cycle numbers or
  process-specific dates into code comments or other explanatory source text.
  Keep tracking history in task records, design records or appropriate commit
  descriptions.
- Avoid phrases such as "per the audit", "this commit", "before this fix" or
  "after the refactor". State the enduring technical requirement directly.
- Apply the same rule to configuration descriptions, manifest text and
  documentation embedded beside code.
- References to public standards, external bugs and named regression classes
  are useful when they explain behavior. An operational audit trail is a
  runtime feature and is not prohibited by this rule.
- Capture durable lessons in repository-local documentation. Do not require
  another checkout or machine-local private memory to understand a comment.
- When removing a procedural reference, retain the technical rationale. Delete
  the comment if nothing useful remains.

Use American English consistently in prose, code comments and documentation.
Avoid churn between regional spelling conventions.

## Verify behavior and keep all Pester tests working

Investigate failures before changing code: read the full error and stack trace,
reproduce the problem and identify its cause. Change one relevant thing at a
time. Do not mask a defect with a workaround that only hides its symptoms.

For a bug fix, add a meaningful regression test, confirm it fails for the
original behavior, then confirm the fix passes. Test observable behavior and
failure paths rather than merely reproducing implementation details.
Difficulty testing is a reason to examine the design, not to skip validation.

Run the repository's documented lint and validation commands. For PowerShell
changes, run PSScriptAnalyzer with the repository's settings and fix findings
after each code change. Keep the code clean and all existing Pester tests
working.

For code changes, run relevant checks during development and the complete
existing Pester suites required by the affected repositories before declaring
the work ready, committing or pushing. Include workspace suites that exercise
changed shared behavior. Use the documented runners and required Pester
versions; a focused test run alone is not evidence that all tests pass.

Never delete or weaken assertions, lower coverage baselines, disable gates or
add skips just to obtain a passing result. Preserve documented platform skips;
report unexpected skips, missing discovery/results and unavailable prerequisites.
If tests still fail (including pre-existing failures), cannot run, or clean code
requires a decision beyond the task's scope, report the evidence and ask the
operator for a human decision before declaring the work complete or proceeding
with a commit/push. Never describe unrun or failing tests as passing.

## Communicate results clearly

Report what changed, why it changed and how it was verified. Include the
commands or evidence that support the result, and distinguish completed checks
from checks that could not run. State material limitations and uncertainty
precisely. When a human decision is needed, explain the blocker and the decision
required without claiming the work is complete.
