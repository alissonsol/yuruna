The canonical prose design lives in [Yuruna Architecture](../architecture.md) and is
**not repeated here**. These six documents are generated by reading the source, and
they visualize what the code does rather than restate what that page says; where a
diagram needs a concept from it, it links. A diagram that disagrees with
`../architecture.md` means one of the two has drifted.

Twenty-nine diagrams across six documents. Every one obeys the same acceptance
rule: no diagram holds more than seven top-level boxes or subgraphs, and no single
parent subgraph's child set holds more than seven children. Where reality holds more, siblings are folded into a named aggregate and the
fold is spelled out in the prose under the diagram; the
[<=7 rule](#the-7-rule----grouping-decisions) section below collects every one of
those folds in one place, so a reader who wants the files behind a box can find them
without opening all six files.

## How they relate

The six build on each other in order, and each answers a different first question.

**Doc 1 gives you the blocks.** Seven of them, derived from the tracked top-level
directories rather than invented, with one node per block so nothing in it can
disagree with doc 2 about how many children a block has. Read it first when the
question is *what are the parts, and what calls what*.

**Doc 2 opens each block.** One section per block, in the same declaration order,
each block expanded into at most seven children with the file list behind every
aggregate. Read it when the question is *which file does this*, or when a box in any
other document needs to be turned back into paths.

**Doc 3 shows what moves between the blocks at runtime.** Six flows, five of them
message exchanges and one a storage layout. Read it when the question is *what
happens when I run this*, or when tracing an artifact -- a planfile, a screenshot, a
failure record, an image -- from the process that writes it to the one that reads it.

**Doc 4 shows the states each long-lived thing passes through.** The runner's own
six-state machine, the per-guest step sequence inside one cycle, the hold on a lab
service that stopped answering, and the warm-resume loop nested inside the workload
step. Read it when the question is *why is it in
this state, and what gets it out* -- a wedged cycle, a pause that will not end, a
guest that keeps being skipped.

**Doc 5 is the data that drives all of it.** Ten entity-relationship views over the
YAML the deploy engine parses, the plan and sequence files the harness resolves, the
runtime state files it writes, and the pool intent store. Read it first when the
question is *what key goes where, and what happens if it is missing*; every edge in
it carries the code reason for its cardinality.

**Doc 6 puts it on machines.** Nodes, listeners, ports, and the gate behind every
optional link. Read it when the question is *what talks to what over the network*,
or *what does this lab still do with the pool tier turned off*.

Two shortcuts worth knowing. A box in doc 3, 4 or 6 that you cannot place is almost
always a doc 2 aggregate, so start there. A field name you cannot find a writer for
is in doc 5's fields tables, which name the module that writes each one.

## The <=7 rule -- grouping decisions

This is the map from a box back to the files. Counts are what the source actually
holds; the fold is what the diagram had to do about it.

### Doc 1 -- Context and Components

The diagram itself folds nothing: seven boxes for seven blocks. The grouping happened
one level up, when the directory listing was reduced to those blocks.

| Decision | What went into it |
|---|---|

## What is deliberately not drawn

Collected from the exclusions the six documents declare.

**Documentation and maintainer trees.** `docs/` and `dev-only/` are not blocks. No
runtime path reads them.

**The `project/` clone.** It exists in a working tree but is gitignored, because
`Update-ProjectClone` deletes and re-clones it at the start of every cycle. Its
contents belong to Project & Global Data and its lifecycle to the Test Harness, so it
is drawn as neither.

**The Pester suites.** All 205 `test/modules/*.Tests.ps1` files are excluded from
every count in doc 2. They mirror the modules they cover, so drawing them would double
the file list without adding a component.

**The stash on the guest fetch path.** No guest script fetches from the stash service.
It is a write sink reached over `scp` / `sftp` from a LAN client and holds no pool
data, so it appears in the storage layout rather than in the fetch sequence.

**The notification latch.** Armed -> N failures -> Fired -> M successes -> Armed, with
counters persisted to `runner.gating.json`. It is a state machine, but it belongs to
the alerting channel rather than the runner and advances once per cycle, so drawing it
would duplicate the outcome edges with different labels.

**The guest quarantine circuit breaker.** Its `none` / `skip` / `release` decision
spans cycles, so it fits neither the per-cycle nor the per-guest frame; the per-guest
diagram shows only where the gate is consulted.

**The remediation recommendation vocabulary.** Seven values from `retry_immediately`
through `escalate`. `Invoke-Remediation` is advisory -- it writes a record and emits an
event and performs nothing -- so it has a classification, not states. The one place a
recommendation changes runner behavior is the gated auto-remediation break-out, which
is drawn.

**Boot recovery's own sequence.** It runs once, before the state machine is
initialized, and is strictly ordered rather than branching, which makes it a data flow
rather than a lifecycle.

**Host and service-VM lifecycles, except one transition.** The caching-proxy,
stash, pool-control and download-agent VMs each have their own start, health and
stop shape driven from `test/service/`, and doc 6 places those VMs without drawing
how they come up. Two qualifications: once per cycle the `service-vm-restore`
preamble powers on any service VM that is registered but stopped -- the one
transition the runner owns -- and the cycle re-checks their readiness at every
sequence step and chain entry, parking itself while one that had been answering is
away. Both are covered in [Lifecycle state](04-lifecycle-state.md), not here.

**The MCP endpoints.** Five daemons mount `POST /mcp` on the port they already
serve and the framework serves MCP over stdio, so the protocol adds no node, no
port and no link -- it is named where the daemons are, in doc 2 and doc 6, and
drawn nowhere.

**Secret values.** Doc 5 carries field names only. No value from a live vault,
transports file or secrets folder appears in any diagram or table.

**Ports Yuruna does not own.** The kube context endpoint and the container registry
address are provider-defined: the engine selects a context and reads a
`registryLocation` output, and never pins either address. Doc 6 leaves the kube
link without a port; the registry link keeps `TCP 5000`, which is the
`global/resources/localhost/registry` case rather than a general truth, and the
prose beside it says so.
